1. Why this project exists

For a GPU kernel, two numbers determine whether it can possibly be fast:

  • FLOPs: how much arithmetic work is required.
  • Bytes: how much data must move through memory.

Their ratio — arithmetic intensity (AI) — tells you whether the kernel is fundamentally compute-bound or memory-bound on a given machine.

Compulsory AI for GEMM — try it

The clearest case: a matrix multiply C = A·B with shapes M×K, K×N, M×N. Algorithmic FLOPs = 2·M·N·K; compulsory bytes = the unique data that must move once = sizeof(dtype) · (MK + KN + MN). The compulsory AI is the upper bound any implementation can possibly achieve.

Why not just use NCU?

NVIDIA's Nsight Compute (ncu) gives measured AI by running the kernel on real hardware. Three reasons that's not always what you want:

  1. It requires running. No good for CI on GPU-less machines, or for design-space exploration ("what if I tile differently?") before the kernel exists.
  2. Measured AI is an execution property, not a kernel property. It depends on launch config, input shape, cache state. Different runs give different numbers.
  3. Static analysis catches what measurement masks. A static FLOP-per-byte count is a theoretical upper bound on what any measurement could see. Comparing the two surfaces gaps (cache reuse, coalescing, divergence) you'd otherwise have to guess at.

What "static" honestly means

The numbers this analyzer produces are requested quantities, not transferred quantities:

  • FLOPs come from counting arithmetic instructions in post-codegen MIR. FMA = 2 FLOPs. Packed-vector f16x2 = 2× lane multiplier.
  • Bytes come from MachineMemOperand sizes, bucketed by address space.

Things this cannot see:

  • Cache reuse — every load counts at face value.
  • Coalescing — a 4-byte access counts as 4 bytes whether perfectly coalesced or fully scattered.
  • Branch divergence — every instruction counted as if all warp lanes execute it.
  • ptxas spills — closed-source assembler downstream of LLVM does its own register allocation.

That's not a flaw to fix; it's the boundary of static analysis. The honest framing: these are the numbers any implementation must do at least, not the numbers a real run will see.

Self-check: predict the AI of c[i] = a[i] + b[i] for fp32 arrays
1 FLOP per element, 12 bytes per element (2 loads + 1 store of 4 bytes each). AI = 1/12 ≈ 0.083 FLOP/byte. Memory-bound on every modern GPU by 2–3 orders of magnitude. We'll verify this on the smoke kernel in §4.

CUDA gets to running code through several intermediate forms. The analyzer lives at one specific point. Click through the tabs to see the same kernel at each stage:

What's here: NVPTX-specific opcodes (FADD_rnf32rr, LD_i32). MachineMemOperands (the trailing :: (load …, addrspace …) annotations) carry size + addrspace. This is what the analyzer reads.
.visible .entry add_kernel(

    ld.param.b64    %rd2, [add_kernel_param_1];
    ld.param.b64    %rd3, [add_kernel_param_2];
    mul.wide.u32    %rd4, %r1, 4;
    add.s64         %rd5, %rd1, %rd4;
    add.s64         %rd6, %rd2, %rd4;
    add.s64         %rd7, %rd3, %rd4;
    ld.global.b32   %r2, [%rd5];
    ld.global.b32   %r3, [%rd6];
    add.rn.f32      %r4, %r2, %r3;
    st.global.b32   [%rd7], %r4;
    ret;
}
What's here: NVIDIA's textual virtual ISA. The add.rn.f32 we saw as FADD_rnf32rr in MIR. Same ld.global we saw with addrspace(1) MMOs. Notice: MMOs are gone — only the .global qualifier remains. Going PTX→MIR would be lossy.
Why MIR, not IR or PTX? IR is too high — types and address spaces aren't yet target-specific, FMA fusion hasn't happened. PTX text is too low — MMOs are gone, parsing is annoying. MIR is the sweet spot: target-specific opcodes already chosen, but MMOs and structural form still preserved. (PTX gets one specific exception: when the kernel uses inline asm, that lowers to an INLINEASM MachineInstr with a literal PTX string body — see §5.)

4. Reading the output, step by step

The analyzer's job: walk the MIR, classify each instruction, accumulate counters, print results. The widget below steps through the smoke kernel exactly as the analyzer does. Click "Step" to advance one MachineInstr at a time — watch the counters update, the highlighted line in the MIR move, and read the commentary below to understand why each instruction either does or doesn't contribute.

build/test/smoke.mir · function add_kernel step through to see the analyzer accumulate

What just happened

You watched the analyzer build up flops=1 flops_f32=1 global_bytes=12 ai=0.083333 by walking each MachineInstr exactly once. Things to take away:

  • The integer ALU instructions don't contribute (ADD64rr, MUL_WIDEu32_ri) — they're for address arithmetic. The classifier uses prefix matching on FADD/FSUB/FMUL/FMA only.
  • param_load=24 doesn't enter global_bytes — kernel-parameter loads come from constant memory at launch, not DRAM during execution. Reported in the diagnostic memory line, excluded from AI.
  • AI is computed against global_bytes, not "DRAM bytes." Local memory (when present) is reported separately as a diagnostic. Reasoning: local rarely matters in well-tuned kernels, and folding it in noises the global signal.
Self-check: predict add_f64.ll's output (same kernel shape, double precision)
1 FLOP in flops_f64 (one FADD_rnf64rr), global_bytes=24 (three doubles at 8 bytes each), AI = 1/24 ≈ 0.0417. Verify with cmake --build build --target test-add_f64 + the manual llc -load … -run-pass=ptx-ai build/test/add_f64.mir -o /dev/null.

5. The f16x2 surprise (and Phase 1's motivation)

Half-precision is the workhorse of modern ML kernels. NVPTX has a packed form (f16x2) where one MachineInstr operates on two halves side-by-side — a 2× lane multiplier baked into the opcode. Under-counting these would silently halve every fp16 kernel's reported FLOPs.

Here's the tricky part: two ways to write the same fp16 fused multiply-add produce dramatically different analyzer output. Toggle between them:

Source: __hfma2 ⚠ analyzer reports flops=0 
#include <cuda_fp16.h>

__global__ void k(const __half2* a, const __half2* b,
                  const __half2* c, __half2* d) {
  int i = threadIdx.x + blockIdx.x * blockDim.x;
  d[i] = __hfma2(a[i], b[i], c[i]);
}

// In MIR (excerpt):
//   INLINEASM &"fma.rn.f16x2 $0, $1, $2, $3;",
//             1 /* sideeffect attdialect */,
//             1572362 /* regdef */, def %14:b32,
//             ...
//             /* clobber */, implicit-def early-clobber $vfp
flops=0 flops_f16=0 global_bytes=16 ai=0.000000
Source: clang vector type ✓ analyzer reports flops=4 
typedef _Float16 v2half __attribute__((ext_vector_type(2)));

__global__ void k(const v2half* a, const v2half* b,
                  const v2half* c, v2half* d) {
  int i = threadIdx.x + blockIdx.x * blockDim.x;
  d[i] = a[i] * b[i] + c[i];   // contracts to FMA with -ffp-contract=fast
}

// In MIR (excerpt):
//   %19:b32 = contract FMA_F16x2rrr %14, %16, %18, 0
flops=4 flops_f16=4 global_bytes=16 ai=0.250000

Why does this happen?

__hfma2 is implemented as a thin wrapper around inline PTX assembly:

asm("fma.rn.f16x2 %0, %1, %2, %3;\n}"
    :"=r"(__HALF2_TO_UI(val))
    : "r"(__HALF2_TO_CUI(a)), "r"(__HALF2_TO_CUI(b)), "r"(__HALF2_TO_CUI(c)));

This becomes an INLINEASM MachineInstr in MIR whose body is the literal PTX string. The analyzer's opcode classifier only sees INLINEASM — it cannot read inside the string. Today the analyzer correctly recognizes the gap (flagged at the MI.isInlineAsm() branch in NVPTXArithIntensityPass.cpp) but contributes zero to the FLOP count.

This is the motivation for Phase 1 of the roadmap. Build a small inline-PTX parser and route what it finds back into the same FLOP/byte counters. The parser only has to handle the bounded set of patterns NVIDIA's own headers emit — verified scrapeable from <cuda>/include/cccl/cuda/__ptx/instructions/generated/ (~60 auto-generated headers covering all of modern PTX).
Self-check: why doesn't this gap show up for fma.ll (scalar f32 FMA)?
The scalar FMA in fma.ll is written in plain LLVM IR (%prod = fmul contract …; %sum = fadd contract …). LLVM's NVPTX backend lowers it to a regular FMA32rrr (or FMA_F32rrr in newer LLVM) MachineInstr, which the classifier recognizes by its prefix. Inline asm is bypassed entirely. The gap only exists for code that goes through CUDA-header intrinsic wrappers like __hfma2, __half2 operator overloads, or any cuda::ptx::* call.

The shape of the per-MI loop

Around line 253 of NVPTXArithIntensityPass.cpp:

for (auto &MI : MBB) {
    if (MI.isDebugInstr()) continue;
    ++Stats.Instrs;
    ++Stats.OpcodeCounts[MI.getOpcode()];

    // INLINEASM integration point: parser+classifier from lib/PTX/
    // will plug in here.

        // TODO: parse asm body, classify each statement, route into
        //       addFlops/recordMemory.
        recordMemory(Stats, MI);
        continue;
    }

    ptxai::OpClass Op = ptxai::classify(TII->getName(MI.getOpcode()));
    if (Op.isFlopProducer()) addFlops(Stats, Op);
    recordMemory(Stats, MI);

This is the only place that decides "what kind of work does an instruction do." Everything else flows from that classification. Notice the if (MI.isInlineAsm()) branch — this is where Phase 1 plugs in.

The classification API

OpClassifier.cpp is ~70 lines. Here's its essence (paraphrased):

OpClass classify(StringRef Name) {
    // Lane multiplier: f16x2/bf16x2/f32x2 process 2 lanes per instruction.
    const uint64_t Lanes =
        (Name.contains_insensitive("f16x2")  ||
         Name.contains_insensitive("bf16x2") ||
         Name.contains_insensitive("f32x2")) ? 2 : 1;

    if (Name.starts_with("FMA"))   return {ScalarFLOP, 2 * Lanes, PerThread, ...};
    if (Name.starts_with("FADD"))  return {ScalarFLOP, 1 * Lanes, PerThread, ...};
    if (Name.starts_with("FMUL"))  return {ScalarFLOP, 1 * Lanes, PerThread, ...};
    if (Name.starts_with("FSUB"))  return {ScalarFLOP, 1 * Lanes, PerThread, ...};

    // TODO: MMA / WMMA / WGMMA → OpKind::MMA, PerWarp scope, FLOPs = 2·M·N·K.
    // TODO: SpecialMath (FDIV, SQRT, RSQRT, EX2, LG2, SIN, COS, RCP).
    return {None};
}

That's the entire MIR-side classifier. Pure function on a StringRef; no MIR context required. Easy to test, easy to extend.

Self-check: where would you add support for FDIV?
lib/OpClassifier.cpp's classify(). Add an else if (Name.starts_with("FDIV")) arm with flopsPerInvocation = 1 * Lanes (by convention, division counts as 1 FLOP for AI purposes despite costing many cycles). Then a test/fdiv.ll copy of fsub.ll with fdiv in place of fsub, registered in test/CMakeLists.txt. About 5 minutes of work — a great first PR.

7. Instruction coverage

Every NVPTX MachineInstr that crosses the analyzer falls into one of four fates. The table below is built from the actual opcodes observed across our test kernels plus the planned-but-not-yet-handled families called out in the roadmap.

Calibration against the canonical opcode list. Mechanically extracting the full NVPTXGenInstrInfo.inc in our LLVM build yields 3568 distinct MIR opcodes. Bucketing each by its TableGen-derived prefix gives this honest coverage map:
  • 2.2% handled (79 opcodes) — the FADD/FSUB/FMUL/FMA prefix family below.
  • 1.1% handled-via-MMO (38) — the LD/ST family below.
  • 4.4% partial (158) — atomics with bytes counted but FLOP side missing.
  • 25.6% correctly ignored (915) — sync, control, integer ALU, mov/cvta, etc.
  • ~63.5% gap (~2264) — opcodes the analyzer scores as zero today but that should contribute. The largest gap clusters: surface ops (762), texture (532), CVT_* conversions (204), TCGEN05 tensor (202), TMA (193), INT_NVVM_* intrinsic-lowered FP arith (186), Hopper async-copy (67).
  • +0.5% handled-via-opcode-name (~18) — the LD_GLOBAL_NC_* / LDU_GLOBAL_* families. These deliberately ship without mayLoad or MachineMemOperand per intentional NVPTX design (D17471, D112466); the analyzer recovers byte traffic via parseMemoryOpcodeName. See the matching row in the table below.
The most consequential gap cluster for compute kernels is INT_NVVM_ADD/SUB/MUL/FMA — 186 opcodes that are the direct lowering of __nv_fma_rn / __nv_fadd_rd-style intrinsics and contain real FP FLOPs the prefix-only classifier misses. This is the same shape of mismatch as the LLVM-18 FMA32rrr case we caught earlier; the table here covers what the analyzer recognizes, not everything that exists in MIR.

Two facts up front, because they reshape how the table reads:

  • Memory bucketing is opcode-agnostic. The same LD_i32 opcode is used for global, local, shared, and constant loads — only the attached MachineMemOperand's addrSpace distinguishes them. That's why the table groups memory ops by behavior, not by mnemonic.
  • FLOP classification is opcode-name-driven. Prefix-match on FADD/FSUB/FMUL/FMA, with a substring check on the type suffix for the precision bucket. This is the entire FLOP detector.

How to read the table when investigating a kernel

Faced with an unexpected analyzer result, the loop is:

  1. Inspect the opcode histogram from the analyzer's per-BB output (FADD_rnf32rr: 1 etc.). It shows every opcode that appeared.
  2. Match each opcode against this table. Anything in "Handled" is contributing; anything in "Ignored" is correctly silent; anything in "Gap" is your suspect for missing FLOPs/bytes.
  3. Anything not in the table at all is a discovery. Add it — usually as either "Ignored" with a note, or "Gap" with a roadmap reference.

This is also the diagnostic flow for the unrecognized bucket the analyzer will eventually print explicitly (after the inline-PTX parser lands).

Self-check: a kernel reports flops=0 but its histogram contains FMA32rrr: 16, FMA_F16x2rrr: 4 on LLVM 18. Bug or correct?
Bug — both FMA opcodes are in the "Handled" row of the FLOP-producing category. Expected: flops = 16·2 + 4·2·2 = 48. If the analyzer reports 0, the classifier dispatch is broken. First place to look: lib/OpClassifier.cpp's prefix-match logic for the version of LLVM you're using. (Historical hint: this is exactly the bug codex flagged when LLVM 18's bare-width FMA32rrr didn't match a stale FMA_ prefix check.)

Decide whether floating-point negation counts as 1 FLOP or 0; the literature is split. Implement, test, and write up the rationale in the commit message. Either choice is defensible if argued well.

Small Special-math classifier expansion ~1 day

EX2, LG2, SIN, COS, RSQRT, RCP — six opcodes, all PerThread, 1 FLOP by convention. Same shape as the FDIV exercise, but more of them, and introduces the OpKind::SpecialMath arm currently a stub in OpClassifier.h.

Medium CCCL scraper (Phase 1, item 1) ~1 day

Walk <cuda>/include/cccl/cuda/__ptx/instructions/generated/, pull out asm template strings and their canonical-PTX comments, write test/ptx-corpus.json. ~100 lines of Python. Output drives the parser/classifier coverage check that gates Phase 1.

Bounded: ~60 input headers, ~2000 patterns total. Mechanical regex work.

Larger Tokenizer + Parser implementation (Phase 1, items 2–3) 3–5 days

The scaffold types are already in lib/PTX/{Tokenizer,Parser}.h. Fill in tokenize() (handle :: in identifiers!) and parse() (recursive descent, per-statement error recovery). Validate against the corpus from the scraper. Pure function, no LLVM dependency in the parser proper — easy to unit-test.

Larger Per-family inline-PTX classifier handlers (Phase 1, item 4) 2–3 days per family

Six families in priority order: FP arithmetic, ld/st, cp.async, MMA, tcgen05, sync/bookkeeping. Each is mechanical — read CCCL docs for the family, write the dispatch arm in lib/PTX/Classifier.cpp, add corpus-coverage assertions.

Larger Tensor-core support on the MIR side (Phase 3) ~1 week

MMA/WMMA/WGMMA opcode classifier with per-arch shape table, plus extending the aggregator to handle PerWarp scope. The assert(scope == PerThread) in addFlops is the canary that fires the moment a PerWarp output appears; replacing it with per-scope buckets is the change.

This is the architectural piece that unlocks ML-roofline analysis. Most modern kernels (attention, GEMM at fp16) are tensor-core bound; without this, their reported FLOPs are radically underestimated.

What I wouldn't recommend as a first PR

  • Anything in Phase 4 (loop / SCEV) — touches both IR-level and MIR-level passes and needs metadata round-tripping. Real architecture work; come back to it after a few smaller PRs.
  • The Reporter abstraction in Phase 5 — meaningful only after JSON output is decided, and that's a UX call best left to a maintainer.

One last frame

This project is a conservative under-counter by design. When the analyzer reports flops=N global_bytes=B, it's saying: "I can prove the kernel does at least N FLOPs and reads at least B bytes; the real numbers may be higher (cache reuse can lower bytes; a known-unknown opcode contributes zero)." The diagnostic line for unknown opcodes exists so you can always see what wasn't classified and decide if it matters. Keep that framing visible in any contribution: it's better to log an "unknown" and produce conservative numbers than to guess and lie.
